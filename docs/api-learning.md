# Booking API — Этап 1: Minimal API (хранилище в памяти)

## Цель

Построить REST API системы бронирования на Minimal API (.NET 10) с хранением данных в памяти.
Главное бизнес-правило: **брони одного ресурса не пересекаются по времени**, в том числе при параллельных запросах.

## Рамки этапа

- Без базы данных и EF Core: данные в памяти процесса, после перезапуска теряются (это ожидаемо).
- Без аутентификации: «кто бронирует» пока передаётся как данные (роли и JWT — тема 18).
- Без библиотек валидации: проверки пишутся вручную или фильтром (полноценная валидация — тема 09).
- Весь код пишу сам. Готовые решения не использую.

## Проектные решения (ответить в README своими словами)

1. **Время.** `DateTime` или `DateTimeOffset`? Как не потерять часовой пояс, если ресурс в одном поясе, а клиент в другом? DateTimeOffset - потому что содержит информацию о таймзоне, клиент отправляет дату вместе с таймзоной
2. **Маршруты броней.** Вложенные (`/api/resources/{id}/bookings`), плоские (`/api/bookings?resourceId=`) или оба? Почему? - плоские, потому что booking это отдельная сущность, которая не всегда связана с ресурсами + отдельный файл с ендпоинтами и mapGroup у нее
3. **Отмена.** Удалять запись или менять статус? Какой HTTP-метод и почему? - Отменяем, владелец ресурса должен видеть, что запись отменили, пропавшая запись = непонятно для пользователя. Patch, потому что мы патчим ентити
4. **Пересечение.** Точное условие пересечения двух интервалов. Брони 10:00–11:00 и 11:00–12:00 конфликтуют? - Нет
5. **Занятый слот.** Какой код возвращать: 400 или 409? Почему? Я выбрал 409 потому что запись конфликтует по времени с уже создаными записями, но думаю и 400 не ошибка.
6. **Недопустимый период.** Что делать, если `from` позже `to` или бронь в прошлом? Какой код? - выбрасываю 400 ошибку, потому что данные для создания не валидные
7. **Хранилище.** Какая структура данных внутри и почему? Как обеспечена потокобезопасность? - Общий стейт + ConcurrentDictionary для каждой entity. Потому что имитация базы данных, потокобезопасность обеспечивается с помощью ConcurrentDictionary. Защита от гонки во время валидации периодов лежит в SemaphoreSlim, мы заставляем при валидации работать только в одном потоке.
8. **По желанию.** Нужны ли strongly-typed IDs (`ResourceId`, `BookingId`)? Обоснование «да» или «нет». - Нет, я использую GUID их достаточно
